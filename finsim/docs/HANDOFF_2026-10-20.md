## 5. Database and persistence rules

This is one of the most important sections.

The previous FinSim architecture suffered from trades appearing in memory and disappearing after restart.

The original investigation found:

- Multiple server processes could write to the same SQLite database.
- Database-locking errors.
- Duplicate event sequence errors.
- Failures silently swallowed by background processing.
- Cached in-memory account state could diverge from SQLite.
- Partially failed commands could persist incomplete events.
- Non-strict event replay could silently skip records.

The new system must correct these problems.

### Required behavior

1. Use SQLite with properly serialized writes and transactional integrity.
2. Journal, events, ledger postings, and affected projections must commit atomically.
3. A failed transaction must leave no partial accounting state.
4. Failed database writes must produce visible errors.
5. Retrying commands must be safe and idempotent.
6. Trades must survive application restart.
7. Account balances must reconcile to ledger balances.
8. Positions must reconcile to executed transactions.
9. Cash, Treasury, and portfolio totals must reconcile.
10. Background processes must not silently discard errors.
11. Prevent multiple server processes from writing to the same database.
12. Never create money through duplicate contributions, subscriptions, or transfers.
